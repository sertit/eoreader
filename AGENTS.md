# EOReader Guide for Coding Agents

This file is the entry point for AI coding agents working in the **EOReader** repository. 
It contains the hard limits, the navigation map, and the verification/self-review process.  
The technical reference (architecture, modules, build & test setup, code style, CI/CD, pitfalls) 
lives in [ARCHITECTURE.md](https://github.com/sertit/eoreader/blob/main/ARCHITECTURE.md).

It follows the [AGENTS.md](https://agents.md/) open format: 
a standard Markdown file at the repository root that coding agents read for setup, testing and convention guidance.

Human contribution guidelines live in [CONTRIBUTING.md](https://github.com/sertit/eoreader/blob/main/CONTRIBUTING.md). 
The project's AI-assisted contribution policy lives in [AI_POLICY.md](https://github.com/sertit/eoreader/blob/main/AI_POLICY.md).

---

## Hard limits (never do these)

- **Never create releases, tags, or version bumps.**
- **Never commit** satellite products, test data, stacks, secrets, or machine-specific paths.
- **Never hardcode** paths, DEMs, credentials, or bucket URLs. Read from the environment (`eoreader/env_vars.py` patterns).
- **Never force dask materialization** inside `load()`/`stack()` pipelines (`.compute()`, `np.asarray`, `rasters.read`).
- **Never act on GitHub without explicit human instruction**: no opening issues/PRs, no posting comments, no tagging maintainers, no labels, no merges.
- **No AI attribution**: no AI tools as authors, co-authors, or credited contributors. No "Generated by ..." anywhere.
- **Never modify CI, pre-commit hooks, or dependency pins** as a side effect of unrelated changes.
- **Never submit** a change the user has not reviewed and does not understand.

## General principles

1. **The human is the author.** Every contribution is owned by the human who submits it. The agent assists and does not contribute on its own. The human must understand every line they submit and be able to explain it.
2. **Maintenance is the scarce resource.** Keep diffs minimal and focused. A change must be worth more to the project than the review time it costs. No speculative refactors, no drive-by cleanups, no "while I'm here" edits.
3. **Respect the sensor-agnostic contract.** New behavior belongs in the generic `Product.load()`/`Product.stack()` API. Constellation specifics stay in the constellation module. Never leak a sensor's quirk into the base class.
4. **Lazy by default.** Do not force materialization inside `load()`/`stack()` pipelines (see [Dask laziness pitfall](ARCHITECTURE.md#common-pitfalls--gotchas)).
5. **No hardcoding.** Paths, DEMs, credentials, bucket URLs: read from the environment (`eoreader/env_vars.py` patterns). Never commit product data.

## Verification checklist (before proposing any change)

An agent must run, and report the results of:

```bash
pre-commit run --all-files                # ruff + format + file checks
python -c "import eoreader"              # import check
python -m pytest ci/on_push/<file>.py --ci_db_dir <local-data-dir>   # if data available
```

If the change touches SAR/SNAP logic, or requires products the agent does not have, the agent must say so explicitly in the PR description and state that CI is the validation path. Never claim a SAR feature works if it was not tested locally or in CI.

An agent must NEVER report a test as passing if it was not run.

## Self-review pass (after the checks)

Before presenting the change to the human, the agent must re-read its own diff and answer each question in the table below. Every "no" must be fixed, or explicitly flagged to the human with a reason. Presenting a diff without this self-review is not allowed.

| #  | Question                                                                                                                 |
|----|--------------------------------------------------------------------------------------------------------------------------|
| 1  | No hallucinated band names or mappings (verified against `band_names.py` and existing constellation modules)?            |
| 2  | Respects the sensor-agnostic boundary (generic behavior in `Product`, sensor specifics in the constellation module)?     |
| 3  | `load()`/`stack()` stay lazy (no forced computation, no whole-file reads from S3 when a window suffices)?                |
| 4  | No hardcoded paths or DEM references (environment variables per `eoreader/env_vars.py`)?                                 |
| 5  | All new band names exported (`eoreader/bands/__init__.py`) and mapped (`band_names.py`, `mappings.py` where applicable)? |
| 6  | CRS, nodata, windows, and resolution handled consistently with existing patterns?                                        |
| 7  | Errors raised as `EoReaderError` subtypes with useful messages?                                                          |
| 8  | Diff is minimal (no drive-by cleanups, no unrelated refactors, no speculative "improvements")?                           |
| 9  | Docstrings, `CHANGES.md` entry, and copyright header present?                                                            |
| 10 | Tests cover the reported behavior, including the edge cases?                                                             |

Report the result in the *AI-assisted review* section of the [pull request template](.github/pull_request_template.md): one short line per accepted or rejected finding, plus which checks were run. Do **not** paste this table into the PR description. The template section is the single record of the self-review.

## Required contribution hygiene

- Add a `CHANGES.md` entry with the right prefix (`FIX:`, `ENH:`, `OPTIM:`, `CI:`, `DEPS:`, `DOC:`, `LINT:`, `TST:`). For mechanical changes, mark it n/a in the PR. Reference the issue it resolves when one exists.
- Follow the commit message conventions in `CONTRIBUTING.md`.
- Use the [pull request template](.github/pull_request_template.md) for every PR and fill out the *AI-assisted review* section.
- Include the copyright header in new files (current release year).
- Update public docstrings for any changed public API.
- Keep PRs small. Break multi-constellation work into separate PRs.
- Reference the existing issue in the PR description. If no issue exists with consensus on the solution, stop and ask the user to open one first.

## Human responsibility & typical AI risks

The human contributor is solely responsible for submitting the PR, understanding every change, and addressing review feedback. AI agents assist but do not submit, merge, or take ownership of contributions (full policy: [AI_POLICY.md](AI_POLICY.md)).

Typical AI failure modes, namely hallucinated band names or mappings, sensor-specific logic leaking into `Product`, verbose code or comments, and hardcoded paths or DEMs, are exactly what the self-review questions above and the [General principles](#general-principles) are meant to catch. When in doubt, verify AI suggestions against existing constellation modules (e.g. `s2_product.py`) before presenting them.
